# תמלול ivrit-ai — אפליקציית נייד

אפליקציית ווב מותקנת (PWA) שמתמללת הקלטות בעברית עם המודלים של
[ivrit-ai](https://huggingface.co/ivrit-ai), בשלושה מסלולים, ואומרת מראש —
לפני שמתחילים — כמה זמן כל מסלול ייקח על **המכשיר הזה**, מה הסיכוי שהוא ייכשל,
וכמה הוא יאט את הטלפון בזמן הריצה.

כתובת: `https://roeepe.github.io/transcribe/`

---

## התקנה בנייד

1. פותחים את הכתובת ב-Chrome (אנדרואיד) או Safari (iOS).
2. תפריט ← **הוספה למסך הבית**.
3. מכאן זו אפליקציה: מסך מלא, אייקון משלה, ועובדת גם בלי רשת (חוץ מהמסלולים בענן).

---

## שלושת המסלולים

| מסלול | איפה רץ | מודל | מהירות טיפוסית | מה צריך להגדיר |
|---|---|---|---|---|
| **על המכשיר** | הדפדפן בנייד, WebGPU | `instush/ivrit-whisper-large-v3-turbo-timestamped-onnx` | פי ‎0.5–1.5 מזמן אמת בנייד חזק | כלום |
| **Colab** | מכונת GPU של Google | `ivrit-ai/whisper-large-v3-turbo-ct2` | פי ‎11–30 מזמן אמת (T4/A100) | Google OAuth Client ID |
| **GitHub Actions** | runner של GitHub, 4 ליבות CPU | `ivrit-ai/whisper-large-v3-turbo-ct2` | פי ‎1.1 מזמן אמת | Client ID + טוקן GitHub + service account |

המסלול המקומי הוא היחיד שבו ההקלטה לא יוצאת מהמכשיר. שני האחרים מעלים אותה
ל-Google Drive שלכם.

---

## הגדרה 1 — Google Drive (למסלולי Colab ו-Actions)

1. [Google Cloud Console](https://console.cloud.google.com/) ← פרויקט חדש.
2. **APIs & Services ← Library** ← להפעיל את **Google Drive API**.
3. **Credentials ← Create credentials ← OAuth client ID ← Web application**.
4. תחת *Authorized JavaScript origins* להוסיף:
   `https://roeepe.github.io`
5. להעתיק את ה-Client ID אל ⚙︎ הגדרות ← Google Drive באפליקציה.

ההרשאה היחידה שמבוקשת היא `drive.file` — גישה **רק** לקבצים שהאפליקציה עצמה
יצרה. היא לא רואה שום דבר אחר ב-Drive. כל העבודה נעשית בתיקייה אחת בשם
`ivrit-transcribe`.

---

## הגדרה 2 — Colab

### מהנייד (הדרך המעשית)

אין טרמינל בטלפון, ולכן ה-CLI של Colab לא רלוונטי שם. במקום זה האפליקציה:

1. מעלה את ההקלטה ל-Drive,
2. יוצרת קובץ תוצאה ריק שהיא תעקוב אחריו,
3. יוצרת עותק של `notebooks/ivrit_transcribe.ipynb` עם מזהי הקבצים כבר בפנים,
4. פותחת אותו ב-Colab.

שם צריך רק לוודא `Runtime → Change runtime type → T4 GPU` וללחוץ
`Runtime → Run all`. אפשר לנעול את הטלפון — המחברת כותבת התקדמות ל-Drive תוך
כדי, והאפליקציה מציגה אותה בזמן אמת (כולל מהירות בפועל וזמן שנותר).

### ממחשב, עם ה-CLI הרשמי

```bash
pip install google-colab-cli        # דורש Python 3.12+, לינוקס או macOS
tools/colab_job.sh shiur.m4a        # -> shiur.json + shiur.txt
```

הסקריפט עושה `colab new --gpu T4` → `colab install` → `colab upload` →
`colab exec` → `colab download` → `colab stop`. אפשרויות שימושיות:

```bash
tools/colab_job.sh -g A100 -k shiur.m4a          # GPU חזק יותר, ולהשאיר את המכונה חיה
tools/colab_job.sh -d 1AbC...xyz                 # קובץ שכבר יושב ב-Drive
tools/colab_job.sh -m ivrit-ai/whisper-large-v3-ct2 shiur.wav
```

`-k` שווה זמן: מכונה שנשארת חיה חוסכת בערך שתי דקות של התקנה בריצה הבאה.

## הגדרה 3 — GitHub Actions ("תמלול על שרת git")

ה-runner מוריד את ההקלטה מ-Drive, מתמלל, וכותב את התוצאה בחזרה לאותו קובץ
תוצאה שהאפליקציה ממתינה לו. ההקלטה עצמה **לא** נכנסת ל-git.

1. **Service account:** Google Cloud Console ← IAM ← Service Accounts ← יצירה ←
   Keys ← Add key ← JSON. שומרים את הקובץ.
2. **סוד במאגר:** Settings ← Secrets and variables ← Actions ← New repository
   secret בשם `GDRIVE_SERVICE_ACCOUNT_JSON`, והתוכן הוא כל ה-JSON.
3. **שיתוף:** ב-Drive, על התיקייה `ivrit-transcribe` ← שיתוף ← להוסיף את
   ה-`client_email` מתוך ה-JSON כ-**Editor**. (האפליקציה גם משתפת כל קובץ
   בנפרד אם הזנתם את הכתובת בהגדרות.)
4. **טוקן:** GitHub ← Settings ← Developer settings ← Personal access tokens ←
   Fine-grained ← המאגר הזה בלבד ← הרשאת **Actions: Read and write**.
   מדביקים בהגדרות האפליקציה. הטוקן נשמר רק ב-localStorage של המכשיר.
5. בהגדרות יש כפתור **בדיקת חיבור** שמוודא שהמאגר, ה-workflow והטוקן תואמים.

ה-runner הוא 4 ליבות CPU בלי GPU. זה בערך פי 1.1 מזמן אמת — כלומר שיעור של
שעה ייקח כשעה — ומגבלת ה-job היא 6 שעות. ההערכה באפליקציה אומרת את זה במפורש
לפני שבוחרים.

---

## איך ההערכה נבנית

זה החלק שלא מנחש. לפני כל הרצה:

1. **מדידה של המכשיר** (`bench.js`) — shader חישובי אמיתי דרך WebGPU ולולאת
   matmul ב-JS, שמחזירים GFLOP/s בפועל. התוצאה נשמרת ל-30 יום כדי לא לחמם את
   הטלפון בכל פתיחה.
2. **עובדות מהדפדפן** (`device.js`) — ליבות, זיכרון, מכסת אחסון פנויה, סוג
   הרשת, מצב הסוללה, זמינות Wake Lock. מה שהדפדפן לא חושף נשאר `null`
   וההערכה מרחיבה את הטווח במקום להמציא ערך.
3. **גודל אמיתי של המודל** (`models.js`) — שאילתה ל-Hugging Face על תיקיית
   `onnx/`, כדי לדעת בדיוק כמה בייטים צריך להוריד בכל וריאנט דיוק, ובדיקה מול
   ה-Cache של הדפדפן כמה מזה כבר נמצא במכשיר.
4. **מודל הזמן** (`estimator.js`) — התפוקה מוצמדת למכשיר ייחוס ומוכפלת ביחס
   המדוד בחזקת 0.75 (התמלול חסום ברוחב פס זיכרון, לא רק ב-ALU), ואז מחושבת
   אינטגרציה של **ויסות תרמי**: אחרי כ-150 שניות של עומס רציף הטלפון מוריד
   תדרים, והתפוקה נשחקת עד כ-55% מהשיא. הזמן שאובד בגלל זה מוצג בנפרד.
5. **סיכון** — לא מספר אחד אלא רשימה: OOM, מקום באחסון, הריגת הלשונית ברקע,
   קטיעת ההורדה, מגבלות buffer של ה-GPU, סוללה שתיגמר. לכל סיכון מוצגים הנימוק
   המספרי והפעולה שמקטינה אותו.
6. **עומס על המכשיר** — כמה מה-CPU/GPU נתפס, כמה פריימים צפויים להיתקע, כמה
   אחוזי סוללה לשעה, ומתי הסוללה תיגמר אם לא מחוברים למטען.

### כיול עצמי

אחרי כל ריצה נשמרים הנתונים שנמדדו בפועל — מהירות, פריימים תקועים, צריכת
סוללה — ונכנסים לממוצע נע (`calibration.js`). מהריצה הראשונה ואילך הכרטיס
מסומן **מכויל** במקום **הערכה**, וטווח אי-הוודאות מצטמצם מ-×1.85 ל-×1.2 בערך.
בתחתית התוצאה מוצג גם דיוק ההערכות עד כה, כדי שיהיה אפשר לראות אם המספרים
אמינים ולא רק יפים.

## פורמטים ואורך

- **WAV** נקרא במקטעים ישר מהדיסק — גם הקלטה של שעתיים לא תופסת זיכרון.
- **פורמטים דחוסים** (m4a, mp3, opus, webm) חייבים פענוח מלא בזיכרון לפני
  תמלול מקומי. לשעתיים זה יכול להיות מעל גיגהבייט, וההערכה מסמנת את זה כסיכון
  OOM ומפנה לענן — שם מעלים את הקובץ הדחוס כמו שהוא, בלי לפענח בנייד.
- התמלול המקומי רץ במקטעים (ברירת מחדל 10 דקות, עם 3 שניות חפיפה). ריצה
  שנקטעת שומרת את המקטעים שכבר הושלמו, וניתן להמשיך מאותה נקודה.

טקסט עם פסקאות, SRT, VTT ו-JSON (כולל חותמות זמן ומטא-דאטה של הריצה).

```
transcribe/            אפליקציית ה-PWA
  js/estimator.js      מודל הזמן, הסיכון והעומס
  js/bench.js          מדידת WebGPU/CPU בפועל
  js/device.js         איסוף יכולות המכשיר
  js/models.js         גדלים אמיתיים מ-Hugging Face + מצב מטמון
  js/audio.js          פענוח, המרה ל-16kHz, חלוקה למקטעים
  js/worker.js         transformers.js בתוך Web Worker
  js/local-run.js      ניהול ריצה מקומית, המשך אחרי קטיעה
  js/google.js         Drive: העלאה מתחדשת ומעקב תוצאה
  js/colab.js          בניית מחברת לעבודה + פקודות ה-CLI
  js/ghactions.js      הפעלת ה-workflow ומעקב
tools/ivrit_transcribe.py   קוד התמלול המשותף (Colab, Actions, מקומי)
tools/colab_job.sh          אוטומציה מלאה עם ה-CLI הרשמי של Colab
tools/build_notebook.py     מייצר את המחברת מתוך הסקריפט
notebooks/ivrit_transcribe.ipynb   נבנה אוטומטית — לא לערוך ידנית
.github/workflows/transcribe.yml   מסלול ה-runner
```

`ivrit_transcribe.py` מוטמע במחברת בייט-בבייט, כדי שהמסלולים לא יתפצלו.
אחרי שינוי בסקריפט צריך להריץ:

```bash
python3 tools/build_notebook.py
```

## מגבלות ידועות

- הרצת התמלול עצמה לא נבדקה מקצה לקצה בסביבת הפיתוח: הגישה ל-`huggingface.co`
  ול-`cdn.jsdelivr.net` חסומה שם, ולכן לא היה אפשר להוריד משקולות אמיתיות.
  נבדקו: זיהוי המכשיר, המדידה, ההערכה, פענוח האודיו, חלוקת המקטעים, פרוטוקול
  ה-Worker, חיבור חותמות הזמן בין מקטעים והייצוא — עם מודל מדומה במקום המשקולות.
- iOS: WebGPU נדרש (Safari 18 ומעלה). בלעדיו המסלול המקומי נופל ל-WASM,
  שהוא איטי בסדר גודל — וההערכה תגיד את זה בפירוש ותציע ענן.
- הערכת ה-uplink נגזרת מה-downlink שהדפדפן מדווח (הדפדפנים לא חושפים uplink),
  ולכן זמן ההעלאה הוא הפרמטר הכי פחות מדויק בהערכה.
- `deviceMemory` מוגבל ל-8 ב-Chrome, כך שבמכשירים עם יותר זיכרון תקציב הזיכרון
  מוערך בחסר — לרעת המסלול המקומי, לא לטובתו.
